2. Optimisation Mémoire Critique : Résolution du Problème OOM (Out-of-Memory) via Swapfile

Avec une instance disposant de 1 Gio de mémoire vive physique, une contrainte majeure est apparue dès les premières compilations de conteneurs : lors de l'exécution de npm run build (le compilateur TypeScript et le bundler Vite de l'interface React), la consommation mémoire atteignait un pic de 1,2 Go. Le noyau Linux déclenchait alors le redouté OOM-Killer (Out of Memory), tuant subitement le processus de compilation avec le code d'erreur 137.

Pour résoudre ce défi d'ingénierie système sans engager de dépenses tarifaires incompatibles avec le crédit étudiant, nous avons configuré une mémoire d'échange (Swapfile) de 2 Go directement sur le disque SSD :

bash — lbetancourtd@WonderWord-vm:~# (Configuration Swap) 
# 1. Allocation d'un fichier de swap de 2 Go sur SSD
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# 2. Persistance dans /etc/fstab pour survie aux redémarrages de la VM
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 3. Réglage de l'agressivité de swap (swappiness = 10 pour privilégier la RAM)
sudo sysctl vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf

Grâce à cette intervention, la mémoire virtuelle disponible est passée à 3,0 Go cumulés, permettant aux compilations Docker de s'exécuter avec une fluidité absolue sans aucun crash système.

Chapitre 02

Conteneurisation Multi-Services avec Docker Compose

Le déploiement applicatif repose sur une architecture conteneurisée orchestrée par Docker Compose. L'adoption de la conteneurisation plutôt qu'une installation native « bare-metal » sur le serveur répond à trois impératifs scientifiques et industriels :

  • Reproductibilité stricte : Élimination du classique biais « ça marche sur ma machine ». Les environnements d'exécution Node.js 24 Alpine et PostgreSQL 17 sont rigoureusement identiques en local et sur Azure.
  • Isolation et sécurité : Les bases de données et les processus internes ne sont pas exposés sur l'Internet public ; ils communiquent au sein d'un réseau de pont privé (wonderword-network).
  • Persistance découplée : Les données utilisateur et les ouvrages littéraires sont stockés dans un volume indépendant du cycle de vie des conteneurs.
Base Relationnelle Port 5432

wonderword-postgres

Image officielle PostgreSQL 17 Alpine. Stockage sécurisé des utilisateurs, tables de hachage bcrypt, jetons de validation d'email, catalogue de livres et progression de lecture. Volume nommé persistant pgdata garantissant zéro perte de données lors des mises à jour.

API REST Backend Port 5000

wonderword-server

Serveur Fastify 5 en TypeScript avec Prisma ORM 6. Intègre l'authentification JWT (7 jours), le hachage bcryptjs (12 rounds), l'API Resend pour les emails transactionnels, et l'API de streaming de chapitres littéraires.

Frontend SPA Port 3000

wonderword-client

Application React 19 + Vite + Tailwind CSS compilée via un Multi-stage Dockerfile. Servie par un conteneur Nginx Alpine ultra-léger avec compression gzip et gestion du routage SPA (fallback index.html).

2. Rôle du Reverse Proxy Nginx sur la Machine Hôte

Sur la machine virtuelle Ubuntu elle-même, un serveur Nginx hôte écoute sur les ports standards 80 (HTTP) et 443 (HTTPS). Il remplit trois fonctions fondamentales :

  • Terminaison SSL/TLS : Nginx négocie le chiffrement cryptographique avec les navigateurs des utilisateurs, déchargeant les conteneurs internes de cette complexité.
  • Routage unifié : Le trafic racine / est redirigé en boucle locale vers le port 3000 (le client React), tandis que les appels aux routes /api/* sont dirigés vers le port 5000 (le serveur Fastify).
  • Redirection HTTPS systématique : Toute tentative de connexion non sécurisée en HTTP (port 80) est automatiquement commutée en 301 Moved Permanently vers HTTPS.
nginx — /etc/nginx/sites-available/wonderword.luisbetancourt.fr 
server {
    server_name wonderword.luisbetancourt.fr;

    # Routage du Frontend React SPA (Port interne 3000)
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Routage de l'API Backend Fastify (Port interne 5000)
    location /api/ {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Certificats SSL générés par Certbot Let's Encrypt
    listen 443 ssl;
    ssl_certificate /etc/letsencrypt/live/wonderword.luisbetancourt.fr/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/wonderword.luisbetancourt.fr/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;
}

Chapitre 04

Pipeline d'Intégration & Déploiement Continu (CI/CD)

L'un des acquis techniques majeurs de cette livraison est l'élimination totale du déploiement manuel. Chaque modification apportée au code source sur la branche main déclenche un pipeline GitHub Actions qui prend le relais en toute autonomie.

1. Architecture du Secret Vault et Connexion SSH Sans Mot de Passe

Pour que les serveurs de GitHub puissent se connecter en toute sécurité à la machine virtuelle Azure sans exposer d'informations sensibles dans le code public, les identifiants sont chiffrés dans les GitHub Actions Secrets :

  • AZURE_VM_HOST : Adresse IP publique statique de la VM (68.210.187.103).
  • AZURE_VM_USER : Compte administrateur Linux sécurisé (lbetancourtd).
  • AZURE_VM_SSH_KEY : Clé privée cryptographique RSA 4096-bit (WonderWord-vm_key.pem).
  • RESEND_API_KEY : Clé secrète de l'API transactionnelle Resend.
yaml — .github/workflows/deploy.yml (Workflow CI/CD) 
name: CI/CD Deploy to Azure VM
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Executing remote SSH commands for deployment
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.AZURE_VM_HOST }}
          username: ${{ secrets.AZURE_VM_USER }}
          key: ${{ secrets.AZURE_VM_SSH_KEY }}
          port: 22
          script: |
            cd /home/lbetancourtd/WonderWord-UNI
            git pull origin main
            echo "RESEND_API_KEY=${{ secrets.RESEND_API_KEY }}" > .env
            docker compose up -d --build
            docker image prune -f

Le cycle complet (téléchargement du différentiel git, injection des variables d'environnement, recompilation différentielle Docker et redémarrage des conteneurs) s'effectue en moyenne en 28 secondes. L'élagage final docker image prune -f libère immédiatement l'espace disque SSD des couches de compilation orphelines.
Chapitre 05

Sécurité RGPD, Authentification & Courriels Transactionnels

Pour respecter les principes du Règlement Général sur la Protection des Données (RGPD) et garantir l'authenticité des comptes apprenants, nous avons déployé un mécanisme d'authentification robuste et moderne.

1. Cryptographie & Mots de Passe : Bcrypt 12 Rounds

Aucun mot de passe en clair n'est jamais consigné en base de données ni dans les journaux d'application. À l'inscription, chaque mot de passe est haché à l'aide de la bibliothèque bcryptjs avec un facteur de coût (salage) de 12 rounds, conférant une protection maximale contre les attaques par force brute ou tables arc-en-ciel.

2. Intégration de l'API Resend pour les Courriels Transactionnels

Plutôt que d'exploiter un serveur SMTP local sujet aux classements en spam par Gmail ou Outlook, nous avons intégré l'API transactionnelle Resend. Chaque nouvel utilisateur reçoit un courriel HTML responsive habillé de l'identité visuelle WonderWord :

  • Confirmation d'inscription : Envoi d'un jeton cryptographique aléatoire de 32 octets. L'utilisateur clique sur le lien, son compte passe au statut email_verified = true et il est connecté automatiquement.
  • Récupération de mot de passe (« Mot de passe oublié ? ») : Génération d'un jeton éphémère (validité stricte de 60 minutes). Dès que le mot de passe est redéfini, le jeton est immédiatement purgé (usage unique) pour prévenir toute réutilisation frauduleuse.
  • Normalisation d'adresses courriel : Nettoyage systématique des espaces et conversion en minuscules (.trim().toLowerCase()) côté frontend et backend afin d'éviter tout doublon insensible à la casse.

2. Fondements Théoriques : Qu'est-ce qu'une API et comment fonctionne-t-elle ?

Une API (Application Programming Interface, ou Interface de Programmation d'Application) est un ensemble de règles, de protocoles et de points d'accès normalisés permettant à deux systèmes informatiques indépendants de dialoguer et de s'échanger des données de manière sécurisée et structurée.

L'Analogie du Restaurant : Comprendre le rôle d'une API

Imaginons un restaurant. Vous êtes assis à table (le client / notre application). La cuisine renferme les ingrédients, les recettes et les cuisiniers (la base de données et le serveur de Gutenberg ou de la BNF). Vous n'avez pas le droit d'entrer directement en cuisine pour fouiller dans les réfrigérateurs : cela créerait un chaos technique et compromettrait la sécurité. C'est ici qu'intervient le serveur (l'API) : il vous présente une carte prédéfinie (la documentation de l'API), prend votre commande précise (la requête HTTP), la transmet en cuisine selon un protocole strict, puis vous apporte exactement le plat demandé dans une assiette standardisée (la réponse au format JSON).

Le cycle fondamental Requête / Réponse

Toute interaction avec une API REST moderne repose sur le protocole standard du Web (HTTP) et se décompose en quatre éléments cardinaux :

  • Le Point de Terminaison (Endpoint URL) : L'adresse web unique désignant la ressource convoitée (ex. https://gutendex.com/books ou https://dracor.org/api/corpora/ger).
  • La Méthode HTTP : L'action souhaitée (GET pour consulter des œuvres sans modifier le serveur, POST pour soumettre ou importer des données).
  • Les Paramètres de Requête (Query Params) : Les filtres appliqués à la demande (ex. ?languages=de&search=Kafka pour isoler les textes allemands de Kafka).
  • La Réponse Structurée (Payload JSON) : Les données retournées sous forme d'arbre d'objets (clé / valeur), universellement compréhensibles par les langages de programmation.

Chapitre 07

Perspectives de Recherche : Le Studio de Shadowing (Phase 3)

Avec une infrastructure cloud pérenne, un système d'authentification validé et une bibliothèque littéraire fonctionnelle, le socle technique est désormais prêt pour la Phase 3 : le laboratoire d'analyse acoustique.

Comme documenté dans le Chapitre 03 de la première livraison, notre choix architectural d'indépendance repose sur un microservice Python utilisant parselmouth (moteur Praat) en mode headless. Ce service sera déployé dans un quatrième conteneur Docker sur le même réseau privé, permettant l'analyse formantique F1/F2 des voyelles critiques françaises sans aucune dépendance vis-à-vis d'API tierces payantes.
